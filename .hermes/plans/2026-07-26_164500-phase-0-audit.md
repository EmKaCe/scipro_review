## Vision

### Why Phase 0 exists before any teacher-mode development

The grading copilot feature set builds on top of the existing SciPro Review codebase. Before adding **anything new**, we need a clean baseline: the existing app must work correctly in every student-facing flow.

The inspection scenarios below mirror what a real student does — selecting an assignment, evaluating a submission, exporting results. If the current app has bugs in these flows:

- **Blocking bugs** would compound with new teacher code, making it harder to debug
- **Cosmetic bugs** would degrade the demo quality for Judith Kennecke (the stakeholder)
- **Any regression** introduced during phase 1-4 would be invisible without this baseline

This phase answers one question: **"Does the app work correctly today?"** The answer is a list of bugs or a clean bill of health.

### What success looks like

After executing every scenario in this plan, we have:

1. A confirmed working (or not-working) list of all user-facing flows
2. Each bug tagged with priority (blocking / major / cosmetic)
3. A GitHub issue documenting findings
4. Blocking bugs fixed before Phase 1 begins

### How this connects to the `main` plan

Per the master plan at `.hermes/plans/2026-07-25_214500-grading-copilot-mastra.md`:

> Phase 0 reveals blocking bugs → Medium likelihood → Fix before proceeding — clean base is prerequisite.

The master plan covers 5 sequential phases. Phase 0 is the foundation — if audit reveals problems, we fix them here. If not, we proceed to Phase 1 with confidence that any regressions we later see are caused by our changes.

> **⚠️ Post-Phase-1 note:** After Phase 1 removes the runtime mode toggle, the following scenarios describe **pre-Phase-1** behavior. When re-running this audit on a post-Phase-1 build, skip or rewrite these:

**Priority definitions:**

|----------|---------|--------|

## Vision

### Why design-first?

The master plan originally treated "Open-design" as a resolved setup issue — the tool was installed but the plan never used it. The corrected workflow puts Open Design in its intended role:

1. **Scope** what we're building (routes, components, data flow)
2. **Design** the visual surface in Open Design (iterate, approve)
3. **Capture** design decisions in a lightweight spec — this becomes **the single source of truth** for implementation
4. **Implement** in SvelteKit — every component follows the approved spec, not the plan's initial sketches
5. **Connect** real data in Phase 3 (API calls replace stub service)

This prevents the common pitfall: building a full Svelte dashboard only to discover layout or interaction issues that should have been caught in mockups.

### Single source of truth flow

```
Phase 2b (OD mockups)
    │
    ▼
Design Decision Record  ←── ALL visual decisions captured here
    │                          (layout, colors, spacing, component
    │                           structure, responsive behavior)
    ▼
Phase 2c (SvelteKit)    ←── Implements what the DDR says,
                             ignoring any earlier plan sketches
```

The 2c implementation tasks in this document contain **only** the non-visual scaffolding (types, data service, TanStack install, header config) and stub behavior specs (what each button does when clicked). The visual layout, color, spacing, and component structure come **exclusively** from the approved OD mockups and the Design Decision Record produced in 2b.

If a 2c task description below mentions a layout detail that conflicts with the approved mockups, the mockups win — update the task before running it.

### How this connects to later phases

| Phase | Delivers |
|-------|----------|
| **2a (Scope)** | Route tree, component hierarchy, data-flow diagram, stub/real matrix |
| **2b (Design)** | Approved Open Design mockups + Design Decision Record (single source of truth) |

| **Phase 3** | API routes replace stub service; polling keeps dashboard live; executor runs notebooks |
| **Phase 4** | LLM suggestions fill the stub buttons; copilot panel per further design decisions |
